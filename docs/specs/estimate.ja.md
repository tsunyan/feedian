# `--estimate` の設計

## 目的

代表的なブックマークの実コンテンツを基に、OpenAI API 料金を予測する読み取り専用の
CLI モードを追加する。Obsidian ノートの作成・更新および OpenAI API 呼び出しは行わない。

## CLI

次の引数を追加する。

```text
--estimate
--estimate-sample-size SIZE
```

`--estimate` は `--list-collections` および `--dry-run` と同時に指定できない。既存の
collection、nested、limit の絞り込みを適用するため、後続の通常処理と同じ対象集合を
見積もる。

`--estimate-sample-size` の既定値は `10%` とし、対象が20件以上の場合は最低20件を
サンプルする。指定形式は次のとおり。

- `20` のような正の整数: 絶対件数
- `10%` または `20%` のようなパーセンテージ
- `0`: ページ取得・コンテンツサンプリングをしない件数ベースの見積り

算出したサンプル件数は対象総数を超えない。不正な値はコマンドエラーとして表示する。

## サンプリング

まず絞り込み済みブックマークのメタデータをすべて取得し、Raindrop のコレクション ID
単位でグループ化する。最大剰余法により、各コレクションの件数に比例してサンプル数を
割り当てる。サンプル数が空でないコレクション数以上なら、すべてのコレクションから
少なくとも1件ずつ取る。少ない場合は剰余の大きいコレクションから割り当てる。

各コレクション内では Raindrop API の順序を維持し、等間隔の中点位置を選ぶ。最初に
返ったブックマークだけに偏らず、各コレクションの順序全体をカバーする。API の結果が
変わらなければ選択結果も一定である。

## トークン数と料金の見積り

ページを取得できる各サンプルについて、Raindian は次を実行する。

1. 通常処理と同じ URL 安全性チェック、本文抽出、長さ制限、タイムアウト、再試行設定で
   ページ本文を取得する。
2. 通常処理で使用するものと同じ LLM プロンプトを組み立てる。
3. `tiktoken` でプロンプトの入力トークン数をローカルで数える。

`OPENAI_API_KEY` は不要である。`tiktoken` は通常の依存パッケージとしてバージョンを
固定する。原則として `encoding_for_model` でエンコーディングを選び、インストール済み
トークナイザーが未知のモデルの場合は `o200k_base` を使い、そのフォールバックを出力に
明記する。

計測した入力トークン数の平均を対象総数に掛けて、入力トークン総数を予測する。各モデル
の料金は、予測入力トークンと対象1件あたりの `max_output_tokens` を使って算出する。
出力には GPT-5.6 Sol、GPT-5.6 Terra、GPT-5.6 Luna、GPT-5.5 を常に含める。
`openai_model` で設定中のモデルには `selected` を明示する。

件数ベースモードではページを取得せず、README に記載した汎用的な入力トークン範囲を使う。
この見積りは精度が低いことを明記する。

## 出力と失敗時の扱い

対象件数、解決後のサンプル件数、取得成功・失敗ページ数、平均入力トークン数、予測入力
トークン総数、設定中の出力トークン上限、経過時間を表示する。続いて、4モデルすべての
単価と見積りを表形式で出力する。

ページ取得の失敗は見積り全体を停止させない。失敗件数と理由を集計し、通常処理と同じく
Raindrop メタデータと取得エラーを含むフォールバックプロンプトをサンプル見積りに使う。
対象が0件の場合は見積りを行わず、その旨を表示する。

## 対象外

- 見積りモードは OpenAI API の呼び出し、ノート生成、Vault への書き込みを行わない。
- サーバー側のリクエスト整形、モデル更新、推論トークンにより、実際の請求額を保証する
  ものではない。
- 取得したページ内容のキャッシュや永続保存は追加しない。

## テストとドキュメント

テストでは、サイズ指定の解析、下限・対象総数による丸め、比例配分、等間隔で決定的な
選択、プロンプトトークン数の計測とフォールバック、読み取り専用の見積り実行、ページ
取得失敗時の扱い、選択中モデル表示、引数競合を確認する。README と設定例には実行方法、
サイズ指定形式、依存関係、対象範囲、制限を記載する。
