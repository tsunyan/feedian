### 1. 完了済みレビューの結論 — 採用

`結論`を、初回の指摘内容・採否・修正後の検証結果を述べる文へ書き換えた。
`指摘`・`採否`・`検証`は変更していない。CodeRabbitが求めた「履歴は変更しないこと」に合致する。

`結論`は指摘が未処理の段階で書かれるため、放置すると必ず修正前の状態が残る。
構造上の問題であり、`規約化した項目`へ移した。

### 2. 確定仕様への改訂追記 — 不採用

`AGENTS.md`の「Revising a final proposal」は、後続の仕様が確定仕様の決定を覆した場合に
**`最終案`の該当箇所を訂正し、`## 改訂`へ追記する**ことを明文で定めている。
節順（`最終案` → `改訂` → `草案` → `レビュー`）、`改訂<N> — <名前> (YYYY-MM-DD)`の見出し、
`(前)`・`(後)`・理由・根拠を記すことまで規定されている。
`docs/specs/20260816-llm-backends.ja.md`の`改訂1`はこの手続きどおりである。

またこの手続きは本リポジトリで既に運用されている。
[Claude Code APIキー対応](../specs/20260821-claude-code-api-key-support.ja.md)と
[画像OCRとSourceノートの完全UUIDファイル名](../specs/20260825-image-ocr-source-filenames.ja.md)は
いずれも`## 改訂`を持つ。指摘を採ると、これら既存文書も規約違反になる。

指摘が挙げる代替（レビュー文書へ記録する）は、**実装が確定仕様から逸脱した場合**の扱いであり、
規約はそれも別に定めている。今回訂正したのは実装の逸脱ではなく、確定仕様の記述そのものが
誤っていた場合であり、規約はこちらに`## 改訂`を割り当てている。両者は排他ではない。

なお指摘2はCodeRabbitの学習事項に基づくものだが、その学習事項は`AGENTS.md`に
`## 改訂`の手続きが加わる前の状態を反映していると見られる。

### 3. 最終案D3とレビュー3の矛盾 — 採用

指摘のとおりである。次の3点で対応した。

1. `docs/reviews/20260816-llm-backends-implementation.ja.md:310`のパスを復元した。
   完了済みレビューは編集前の状態に戻り、`レビュー3`の決定と一致する。
2. 仕様に`## 改訂`を新設し、`改訂1`として最終案D3と「変更するファイル」の表を訂正した。
   あわせて確定事項4の見出しと確定事項6の除外条件も、`レビュー3`後の状態へ揃えた。
3. 英語版`docs/specs/llm-backends.md`の削除は維持した。`レビュー3`が
   「英語版の削除自体は採用し」と明記しているためである。

`レビュー3`の論拠は成立する。`:310`のパスは、誤って参照した草案が**英語版**であったことを
特定する情報であり、除去すると「確定前の草案を参照し」となってどちらの草案か分からなくなる。
また当該レビューの対象コミット`7e9d09e`にはこのファイルが含まれ、
`git show 7e9d09e:docs/specs/llm-backends.md`で今も取得できるため、
作業ツリーから削除してもレビューの再現性は損なわれない。

**原因は手続きの側にある。** `最終案`を書く直前、編集ツールは対象ファイルが
ディスク上で変更されていることを通知していたが、執筆者はファイルを読み直さずに書いた。
その結果、追記されていた`レビュー3`を反映しないまま`最終案`が確定した。
`規約化した項目`へ移す。
