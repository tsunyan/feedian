## 指摘

### 1. 移行カウンタを「新規則下で観測した回数」と説明している — 重大度: 低

**根拠:** `feedian/store.py:2013-2026`、`DESIGN.md:59`、確定仕様`:92-105`、`tests/test_store.py:1739-1778`

**現象:** `_migrate_v8_to_v9`のdocstringは、`terminal_kind_failures`を「新規則の下で観測した連続失敗」と説明し、既存回数のリセットによって同じ意味へ揃えるとしている。`DESIGN.md`も同じ説明を記載する。しかし実装は既存の`consecutive_failures >= 2`を**0ではなく1**へ戻す。移行で設定した1は新規則の下で観測した失敗ではなく、移行後の単発障害で終端にしないための正規化された基準値である。

確定仕様の最終案はこの点を明示し、移行後に必要な失敗は2回、既存`fetched_at`が古ければ移行直後にdueとなる、と定めている。実装と回帰テストもそのとおりである。誤っているのはコメントと設計要約だけである。

**影響:** 現在の実行結果は壊れないが、保守者が説明を正とすると、1を実観測値と誤認してmigrationを0へ変えたり、閾値到達まで3回の新規失敗が必要だと判断したりする。これは、単発DNS障害を防ぎつつ追加取得を1回に抑えるという確定判断を将来の変更で崩す。

**提案:** `_migrate_v8_to_v9`のdocstringと`DESIGN.md:59`を、「既存の高い回数を1という基準値へ正規化し、移行後の一時障害1回では終端にしない。移行後2回の失敗で閾値3へ達する」という実動作へ直す。SQLとテストは変更しない。

### 誤りの出所は確定仕様の文面にある

この説明は実装者が創作したものではない。確定仕様の最終案`:92`が「`terminal_kind_failures`は「新規則の下で観測した連続失敗の回数」として定義される」と述べており、docstringはこれを引き写している。実装者への委譲仕様にも同じ表現が入っていた。

同じ最終案は、他の箇所で実動作を正確に述べている。「リセット後、終端に達するには**移行後の失敗が2回**必要である」（`:94`）と、「**0ではなく1である。**」およびその理由（`:109`）である。したがって仕様は結論としては正しく、リセットを決めた根拠を要約した`:92`の一文だけが緩い。指摘が「機能上の不具合は見つからなかった」としているのはこのためである。

**確定仕様は編集しない。** リセット先が1である意味を確認する読者は、`:92`の一文ではなく`:94`・`:109`、本レビュー、および`DESIGN.md`を見ること。
