## 指摘

### 1. 確定仕様が実装と同じコミットに入っている（Codex, P1） — 重大度: 高（主張）

**主張:** 「このファイルは`確定`だが、コミット`ceb74d15`が実装と一緒に`feat:`コミットで導入している」。

**検証結果: 事実誤認。**

```
$ git show --stat --format= 7a3249a
 docs/specs/20260818-fetch-retry-suppression.ja.md | 614 ++++++++++++++++++++++
 1 file changed, 614 insertions(+)
```

仕様は`7a3249a`で**単独・`docs:`型**でコミットされ、実装`859c6bb`はその後である。`ceb74d15`はこのリポジトリに存在しないオブジェクトである。

### 2. `対象`が直前のコミットを指していない（Codex, P1） — 重大度: 高（主張）

**主張:** 「レビュー対象の履歴において`859c6bb`はこのコミットの親ではなく、祖先ですらない。実際の親は`ed74e3c`である」。

**検証結果: 事実誤認。**

```
$ git rev-parse --short f758fcb^

$ git merge-base --is-ancestor 859c6bb f758fcb && echo ancestor

```

`859c6bb`は`f758fcb`の**直接の親**である。

### 3. レビュー文書を変更セットから外すべき（CodeRabbit, Minor） — 重大度: 低

**主張:** 「`docs/reviews/*.ja.md`の指示は、所見を書いてもコミットしないことを要求している」。

**検証結果: 規約の読み違い。** 引用されているのはライフサイクルの手順1であり、手順3を無視している。

> 1. **Write the findings** — Do not commit it.
> 3. **Complete it** — Fill in `採否` and `検証`, set the status to `完了`, and commit the document **in the same commit as the fixes**.

さらに同じ節は「Reviews are published. Never place `docs/reviews/` in `.gitignore`.」と定めている。**レビュー文書はコミットされることが前提である。**

### 4. 確定仕様と実装の`warning`状態遷移が一致していない（CodeRabbit, Major） — 重大度: 中

**根拠:** 仕様書`:103-108`、`feedian/store.py`、`DESIGN.md`

**現象:** 確定仕様の状態遷移表は、非空本文の成功時に`warning`をNULLにすると定めている。実装はRSSフォールバックの由来を残すため`warning`を保持し、`DESIGN.md`とテストもその挙動を固定している。

**影響:** 将来の実装者が確定仕様に従い、フォールバック由来の情報を消す変更を入れ得る。

### 指摘1・2の原因 — レビュー対象が実際の履歴ではない

**2回連続で同じ2件が出たため、原因を特定した。** GitHubがPRごとに生成する merge preview ref を見ると次のようになっている。

```
$ git fetch origin refs/pull/16/merge:refs/tmp/pr16merge
$ git log --oneline -1 refs/tmp/pr16merge
8a8dd11 Merge f758fcb7... into ed74e3c1...
```

Codexが「実際の親」と述べた`ed74e3c`は、この合成コミットの第1親、すなわち**ベースブランチの先端**である。存在しない`ceb74d15`も同種の一時オブジェクトと考えられる。

つまりCodexは、**PRの変更を1つに潰した合成オブジェクト**をレビューしている。その視点からは、

- 3つのコミットが1つに見える → 「仕様が実装と一緒にコミットされている」
- 親がベース先端 → 「`859c6bb`は親ではない」

の2つが**いずれも真である。** 実際の履歴に対しては、いずれも偽である。

**したがってCodexの不具合でも、規約自体の誤りでもない。視点の不一致である。** `AGENTS.md`のライフサイクル規約のうち、この2つだけが**ファイル内容ではなくコミット位相についての主張**であり、PRの潰れた差分では位相が構造的に失われる。規約どおりに実装した全PRで、この2件は毎回再現する。

こちら側で打てる手は、**検証手順を規約に書くこと**である。「PRの差分ではなく`git log`で確認する」と明記すれば、自動レビューにも人間のレビュアーにも判断材料が渡る。規約化した（後述）。

### 指摘4を修正して採用した理由

仕様と実装が食い違っているという指摘は正しい。ただし**提案されている「仕様を更新するか、実装を仕様どおりに変更する」の両方を採らない。**

- **仕様は編集しない。** `AGENTS.md`は「確定した仕様は決して編集しない。実装が確定仕様から逸脱した場合、レビュー文書がその逸脱と決着を記録する場所である」と定めている。逸脱は[実装のコードレビュー](20260818-fetch-retry-suppression-implementation.ja.md)に記録済みである。
- **実装も変更しない。** 判定（`should_fetch_resource`の失敗分岐、`unfetched_resources`の候補判定、`terminal_failure_count`）はいずれも本文長0を必須条件とするため、warningのNULL化は機構上不要である。一方、消すとRSSフォールバックが本文とページ取得エラーを同時に記録した理由が失われ、raw noteの`## Fetch Warning`が示す情報が消える。

**採ったのは指摘の背後にある懸念、すなわち発見可能性である。** 逸脱がレビュー文書にしか無いと、仕様だけを読んだ実装者が気づけない。`DESIGN.md`の該当行へ、この1点が確定仕様と異なること、その理由、レビュー文書へのリンクを追記した。`DESIGN.md`は「現在どう動いているか」を扱う可変の文書であり、仕様は「なぜそう決めたか」を扱う不変のADRである。読者が実装に従う経路は`DESIGN.md`であり、そこに逸脱を書けば懸念は解消する。

## 規約化した項目

**指摘1と2は、PR #15のレビューでも同一の2件が出ている。** 同じ指摘が2回目のレビューで現れたため、`AGENTS.md`へ規約として昇格した。

仕様のライフサイクル手順3・4と、レビュー文書の`対象`について、**検証はPRの差分ではなくブランチの`git log`で行う**ことを明記した。あわせて、なぜPRの視点では常に偽陽性になるのかを書いた — PRは変更をベース先端を親とする1つの潰れたオブジェクトとして提示するため、これらの手順が作る境界そのものが失われる。

これにより、次回以降のレビュアーは指摘を出す前に検証手段を持てる。それでも同じ指摘が出た場合は、レビュアー側の視点の問題として本文書と同じ反証を提示すれば足りる。
