## 指摘

### 1. DNS接続が再解決するとする説明は現行実装と逆 — 重大度: 中

`README.md:775`は、アドレス検査後に接続がホスト名を独立に再解決すると説明している。
現行の`feedian/extract.py:138-170`は`getaddrinfo`を1回だけ実行し、検査済みの
`sockaddr`へ直接接続してDNSをピン留めする。再解決は行わない。READMEの説明は
DNS rebinding対策の現状を逆に伝え、利用者とレビュー者がセキュリティ境界を誤解する。
「名前解決は1回だけ行い、検査済みアドレスに接続する」と直す必要がある。

### 2. `openai-responses`をbuilt-in defaultとする表が解決順の説明と矛盾する — 重大度: 中

`README.md:111`は`openai-responses`を「The built-in default backend」とするが、
`README.md:434`は正しく「Vault config is the real default, not a built-in constant」と説明している。
実装は`--backend` / legacy alias / 環境変数 / Vault configの順で解決するため、
別backendを設定したVaultでOpenAIがbuilt-in defaultとして選ばれることはない。
同じREADME内で判断の異なる2つの説明が残り、仕様A3が解消対象にした誤解を
認証表で再導入している。`feedian init`が作る初期設定であることを述べる表現へ直す。

### 3. 新設した削除条件を英語版の削除が満たしていない — 重大度: 中

`AGENTS.md:33-36`は、規約制定前の文書を削除できるのは、その内容が規約に従う
文書へ「absorbed verbatim」され、削除を改訂として記録した場合だけと定めた。日本語版は
この条件を満たすが、同コミットで削除した`docs/specs/llm-backends.md`は英語版である。
`docs/specs/20260816-llm-backends.ja.md:173-177`も、それを「同一内容の翻訳」と記録するだけで、
英語の内容をverbatimに取り込んだとはしていない。そのため、追加後の規約を同じコミットが
満たしていない。「無日付であることだけを理由に改名または削除しない」という、
実際の決定に合う条件へ直す必要がある。

### 4. 仕様が要求する相対リンク検査が通らない — 重大度: 中

確定仕様`docs/specs/20260827-documentation-consistency.ja.md:113-114`は、`README.md`と`docs/`の
全相対リンクが解決することを検証条件にしている。現行treeでは9リンクが解決しない。
例えば`docs/specs/20260821-claude-code-api-key-support.ja.md:456`はWindowsの区切りと`:L544`を
リンク先に含め、`docs/specs/20260825-image-ocr-source-filenames.ja.md:1050`は同じ`docs/specs/`内から
再び`docs/specs/`を付けたパスを参照する。どちらも通常のMarkdown相対リンクとして
解決できず、読者は根拠文書やソースへ辿れない。仕様の検証範囲を絞るか、対象リンクを
意味を変えない書式訂正として直す必要がある。

### 5. 確定仕様の変更ファイル一覧に無い`.env.example`を同コミットで変更した — 重大度: 低

確定仕様`docs/specs/20260827-documentation-consistency.ja.md:95-103`は実装対象を7ファイルに
限定しているが、`0534240`は`.env.example:6,9`も変更した。変更内容自体はREADMEと
一致しており妥当だが、確定後に暗黙に実装範囲を広げたため、仕様の変更ファイル一覧が
実装の完全な記録ではなくなった。採用するなら、レビューの採否でこの乖離と理由を記録する。

### 1. DNS再解決の説明が実装と逆 — 採用

`feedian/extract.py:138-170`の`_validated_create_connection`は`getaddrinfo`を1回だけ実行し、
返った全アドレスを検査したうえで、その同じ`sockaddr`集合の中だけへ接続する。docstringも
「the hostname is never re-resolved between the check and the connect」と明記し、
`socket.create_connection`を使わない理由まで述べている。指摘のとおりREADMEは逆を書いていた。

この文は`4f016dc`（Manusバックエンド追加）で書かれたものであり、
[フェッチ・設定・復元の境界強化](../specs/20260820-fetch-config-integrity-hardening.ja.md)による
DNS pinning導入より前の記述が残っていた。仕様のA1〜A6は列挙していなかったが、
「READMEを実装へ追従させる」という本仕様の目的そのものに該当し、
かつセキュリティ境界を実際より弱く伝える誤りであるため採用する。

修正時に、browser fallbackの残存TOCTOUを1文添えた。`DESIGN.md`の
「Chromium内部の名前解決と検証の間のTOCTOUは残存リスクとして受け入れる」に対応する。
指摘は求めていないが、direct fetchだけを直すと今度は逆向きに過大な保証になるためである。

### 2. built-in defaultの表記が解決順と矛盾 — 採用

同じREADME内で、認証表が`openai-responses`を「built-in default」と呼び、
解決順の節が「Vault configこそが既定であって組み込み定数ではない」と述べていた。
仕様A3が解消対象にした誤解を、私が別の場所で再導入していた。
表のセルを「`feedian init`がVaultの初期`llm.backend`として書き込む値」へ改めた。

### 3. 新設した削除条件を英語版の削除が満たさない — 修正して採用

指摘は正しい。`AGENTS.md`へ書いた「absorbed verbatim」という条件は、
日本語版の削除は説明できるが、同じコミットで削除した英語版`llm-backends.md`を説明できない。
規約を追加したコミット自身がその規約を満たしていなかった。

ただし指摘が示す「無日付であることだけを理由に改名または削除しない」へ**置き換える**案は採らない。
それは削除を許す条件を規約から消してしまい、今回実際に行使した判断が規約の外に出る。
条件は残したまま、翻訳元が残る場合を含む表現へ書き直し、
指摘の一文は「無日付であることは、それ自体では改名や削除の理由にならない」として併記した。

### 4. 相対リンク検査が未達 — 修正して採用

確定仕様の検証条件4は`README.md`と`docs/`の全相対リンクが解決することを求めており、
9件が未達だった。前回の報告でこれを「範囲外」としたが、
**確定仕様が課した検証条件を満たさないまま完了とするのは誤りである。** 指摘のとおり。

指摘は「仕様の検証範囲を絞るか、リンクを修正するか」の二択を示している。**リンクの修正を採る。**
無関係な既存不具合に合わせて確定仕様の検証条件を弱めると、その条件が次に守られる保証が消える。
またこの9件は読者が根拠文書やソースへ辿れないという実害を持つ。

なお指摘の診断は一部不足していた。指摘はWindowsの区切りと`:L544`、および
`docs/specs/`の二重付与を挙げるが、`20260821`の7件はそれらを直しても解決しない。
リンクが文書の位置ではなくリポジトリルートからの相対で書かれているためで、
`../../feedian/llm_backends.py`と`../reviews/`まで直して初めて解決した。

対象はいずれも確定仕様の`草案`・`レビュー`節、すなわち追記専用の領域にある。
規約が認める「意味を変えない訂正」として扱い、**リンク先の文字列だけを変更した。**
リンクテキストと本文は1文字も変えていないため、その節を参照するレビューの記述は影響を受けない。

### 5. `.env.example`が仕様のファイル一覧に無い — 採用

確定仕様の「変更するファイル」は7件だが、実装は`.env.example`も変更した。
READMEの認証ブロックは「`.env.example`をコピーせよ」と指示しており、
`OPENAI_MODEL`の既定値と`LLM_PROVIDER`→`LLM_BACKEND`を片方だけ直すと両者が食い違う。
変更自体は妥当だが、確定後に暗黙へ範囲を広げた点は指摘のとおりである。
`0534240`のコミットメッセージに明記したうえで、ここに乖離として記録する。
仕様書は改訂しない。実装の記録はこのレビュー文書が持つ、というのが規約の分担である。
